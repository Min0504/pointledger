# 격리수준 실험 기록 — lost update는 어떻게 생기고 무엇이 막는가

> 실험 전체는 실행 가능한 테스트로 저장소에 보존되어 있다.
> 재현: [PR #2](https://github.com/Min0504/pointledger/pull/2) · 비교 실험: [experiment/optimistic-retry](https://github.com/Min0504/pointledger/tree/experiment/optimistic-retry) 브랜치

## 1. 재현 — READ COMMITTED에서 잔액이 증발한다

같은 지갑(잔액 10,000P)에 5,000P 사용 요청 2개가 동시에 들어온다.

```text
TX-A                                TX-B
─────────────────────────────────────────────────────────────
SELECT balance → 10,000
                                    SELECT balance → 10,000   ← 같은 스냅샷
검증: 10,000 ≥ 5,000 OK
                                    검증: 10,000 ≥ 5,000 OK
UPDATE balance = 5,000
COMMIT
                                    UPDATE balance = 5,000    ← A의 커밋을 덮어씀
                                    COMMIT
─────────────────────────────────────────────────────────────
결과: 잔액 5,000 (기대 0) — 5,000P가 회사 손실로 증발
```

- PostgreSQL 기본 격리수준 READ COMMITTED는 **각 문장 시작 시점의 스냅샷**을 읽는다.
  두 트랜잭션 모두 "10,000"을 읽는 것은 버그가 아니라 스펙이다.
- `ExecutorService` + `CountDownLatch`로 동시 100요청을 쏘는 재현 테스트가
  락 없는 커밋에서 실패하는 상태로 이력에 남아 있다 (red → green 커밋 쌍).

## 2. 격리수준별 관찰

| 격리수준 | 동작 | 채택 여부 |
|----------|------|-----------|
| READ COMMITTED (기본) | 두 TX 모두 낡은 잔액을 읽음 → lost update | 그대로는 불가 |
| REPEATABLE READ | 나중 커밋이 `could not serialize access` 실패 → 전면 재시도 필요 | 재시도 루프 비용, 부분 채택 여지 |
| SERIALIZABLE | 직렬 실행과 동등 보장, 충돌 시 실패율 급증 | 핫 지갑(같은 행 경합)에 부적합 |
| **READ COMMITTED + FOR UPDATE (채택)** | 지갑 행 락으로 경합 지점만 직렬화 | ✅ |

격리수준을 올리는 것은 "충돌을 감지하고 실패시키는" 전략이고, 행 락은 "충돌을 기다리게 하는" 전략이다.
포인트 차감은 **재시도보다 대기가 싼 워크로드**다 — 충돌 시 해야 할 일이 어차피 "다시 읽고 다시 차감"이므로,
실패→재시도 루프는 같은 일을 더 비싸게 할 뿐이다.

## 3. 채택 — 지갑 행 비관적 락

```sql
SELECT * FROM wallets WHERE user_id = ? FOR UPDATE
```

- **락 단위 = 지갑 행.** 같은 지갑의 변화만 직렬화되고, 다른 지갑끼리는 완전히 병렬이다.
- 지갑 행 락이 그 지갑의 로트·원장까지 보호한다 — 모든 쓰기 경로가 "지갑 락 먼저" 규율을 지키기 때문
  (`LedgerService`가 유일한 창구라서 가능한 규율).
- 데드락 예방: 락 획득 순서가 항상 "지갑 → 로트"단방향이고, 지갑 두 개를 동시에 잡는 경로가 없다.

검증(락 적용 후 같은 시나리오):

| 시나리오 | 결과 |
|----------|------|
| 동일 지갑 동시 redeem 100 스레드 | 잔액 정확, CHECK 위반 0, 원장 합계 == 잔액 |
| 잔액 부족 경계(마지막 1건만 성공 가능) | 정확히 1건 성공, 99건 `INSUFFICIENT_BALANCE` |

## 4. 비교 실험 — 낙관적 락은 왜 채택하지 않았나

`experiment/optimistic-retry` 브랜치에 `@Version` + 재시도 루프 구현이 보존되어 있다 (머지하지 않음).

| 관점 | 비관적 락 (채택) | 낙관적 락 + 재시도 |
|------|-----------------|-------------------|
| 핫 지갑 경합 | 대기 후 전원 성공 | 충돌 → 롤백 → 재시도 폭증 (동시 100에서 수백 회 재실행) |
| 처리량 (경합 워크로드) | 안정 | 재시도가 DB 왕복을 배수로 늘림 |
| 코드 복잡도 | 락 한 줄 | 재시도 정책·백오프·최대 횟수·실패 처리 |
| 적합한 곳 | 충돌이 잦은 자금성 데이터 | 충돌이 드문 데이터 (프로필 수정 등) |

결론: **충돌이 일상인 도메인에서 "충돌은 예외"라는 가정(낙관)은 성립하지 않는다.**

## 5. 남은 것 — 락이 못 막는 것들

행 락은 동시성만 해결한다. 다음은 별도 장치가 막는다.

| 위협 | 방어 |
|------|------|
| 재시도로 같은 요청 2회 도착 | 멱등성 키 — [PR #3](https://github.com/Min0504/pointledger/pull/3) |
| 락 규율을 우회하는 미래의 코드 | CHECK(`balance >= 0`) + 부분 UNIQUE + append-only 트리거 |
| 그래도 틀어진 잔액 | 일일 대사가 `SUM(ledger) == balance` 검증 — [PR #6](https://github.com/Min0504/pointledger/pull/6) |
