# Incident 리포트 — 원장 우회 조작을 대사가 잡아내는가 (모의 훈련)

| 항목 | 내용 |
|------|------|
| 일시 | 2026-08-14 (모의) |
| 유형 | SNAPSHOT_MISMATCH — 지갑 잔액 ≠ 원장 합계 |
| 영향 | 지갑 1개 잔액 +500P 과다 (실제 사용자 영향 없음 — 훈련 데이터) |
| 결론 | **대사 배치가 1회차 실행에서 즉시 발견.** 자동 수정 없이 이슈 적재 → 운영자 정정 절차로 종결 |

## 1. 시나리오 — 왜 이 훈련인가

append-only 원장과 계층 방어(락·트리거·CHECK)는 **애플리케이션을 경유하는** 모든 조작을 통제한다.
남는 위협은 그 바깥이다: DBA의 수동 UPDATE, 마이그레이션 스크립트 실수, 백업 복원 후 부분 유실.
이 훈련은 "통제 밖 조작이 발생했을 때 시스템이 그것을 **발견**하는가"를 검증한다.

## 2. 재현 방법

```sql
-- 애플리케이션을 우회해 DB에 직접 접속, 원장 없이 잔액만 조작
UPDATE wallets SET balance = balance + 500 WHERE user_id = 44;
-- 이 시점: 원장 합계 3,000P vs 지갑 잔액 3,500P
```

```bash
# 일일 대사 실행 (평소엔 06시 cron)
POST /admin/batch/reconcile/run {"reconcileDate": "2026-08-14"}
```

## 3. 관찰된 동작

1. 대사 1단계(스냅샷 대사)가 `SUM(ledger_entries) != wallets.balance`를 검출:

```text
reconcile_issues
  issue_type = SNAPSHOT_MISMATCH
  wallet_id  = 3
  expected   = 3000   ← 원장 기준 (진실)
  actual     = 3500   ← 지갑 스냅샷 (오염)
```

2. 대시보드 "미해결 대사 이슈" 카운트 증가, 어드민 [대사 이슈] 탭에 노출.
3. **잔액은 수정되지 않았다** — 설계된 동작. 자동 정정은 원인 조사를 불가능하게 만든다.
4. 원인을 정정하지 않고 이슈만 "해결 처리"한 뒤 대사를 재실행하자 **같은 불일치가 새 이슈로 다시 적재**됐다.
   이슈 종결은 검토 표시일 뿐, 데이터가 맞을 때까지 대사는 계속 소리를 낸다.

## 4. 정정 및 종결

[운영 runbook §1](../operations.md) 절차를 그대로 수행:

```text
1. 식별  이슈 목록에서 SNAPSHOT_MISMATCH / 지갑 3 / 기대 3,000 / 실제 3,500
2. 조사  지갑 타임라인 열람 — 원장에는 +500에 해당하는 행이 없음 → 우회 조작 확정
3. 정정  ADMIN_REVOKE 500P, 사유: "이슈 #N — DB 직접 조작 복구" (원장에 기록됨)
4. 종결  이슈 해결 처리, 메모에 정정 원장 번호 기재
5. 확인  다음 대사 실행에서 재적재 없음 = 데이터 정합 복구 완료
```

## 5. 배운 것

- **발견과 수정의 분리가 감사 가능성의 핵심이다.** 대사가 몰래 고쳤다면 이 조작은 영원히 묻혔다.
- 기대값의 기준은 항상 원장이다. 스냅샷(잔액)은 파생값이므로 "무엇이 진실인가"에 논쟁의 여지가 없다.
- 같은 불일치의 재적재(해결 후에도)는 버그가 아니라 기능이다 — 근본 원인 미해결을 시스템이 기억한다.

## 6. 관련 검증 코드

- `ReconcileJobIntegrationTest` — 지갑 오염 → SNAPSHOT_MISMATCH 적재, 미해결 중복 방지, 해결 후 재발견
- `SettleJobIntegrationTest` — 확정 정산 동결, 늦은 취소의 DRAFT 재계산
