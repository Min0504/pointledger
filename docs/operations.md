# 운영 Runbook

운영자가 어드민(<http://localhost:5173>)과 API로 수행하는 절차를 정의한다.
원칙: **모든 정정은 원장에 남는다. 잔액을 직접 고치는 절차는 존재하지 않는다.**

## 1. 대사 이슈 정정 절차

대사 배치(06시)가 불일치를 발견하면 `reconcile_issues`에 적재되고 대시보드에 경고가 뜬다.
**시스템은 자동으로 아무것도 고치지 않는다** — 아래 절차가 유일한 정정 경로다.

```text
1. 식별   어드민 [대사 이슈] 탭 — 유형·대상·기대값(원장 기준)·실제값 확인
2. 조사   [지갑·원장] 탭에서 해당 지갑 타임라인 열람
          - SNAPSHOT_MISMATCH: 원장 합계와 잔액이 다르다 → 원장 우회 조작 흔적 (DB 직접 접근 등)
          - EXTERNAL/INTERNAL_MISSING: 한쪽에만 있는 거래 → 주문 서버 로그와 대조
          - AMOUNT_MISMATCH: 양쪽 금액 불일치 → 멱등성 키 재사용 오류 여부 확인
          - SETTLEMENT_DRIFT: 확정 정산 이후 늦은 취소 → 다음 정산 주기 조정 대상
3. 정정   잔액 정정이 필요하면 [지급·회수] 화면에서 ADMIN_GRANT/REVOKE
          - 사유(reason) 필수 — 원장에 운영자 이메일과 함께 영구 기록
          - 이슈 번호를 사유에 남긴다 (예: "이슈 #12 — 수동 DB 조작 복구")
4. 종결   이슈의 [해결 처리] — 처리 근거 메모 필수
          해결 처리는 검토 완료 표시일 뿐이다. 원인을 정정하지 않고 닫으면
          다음 대사가 같은 불일치를 새 이슈로 다시 적재한다 (설계된 동작)
```

모의 훈련 기록: [incident/2026-08-14-snapshot-mismatch.md](incident/2026-08-14-snapshot-mismatch.md)

## 2. 배치 운영

### 정상 스케줄

| 시각 (KST) | Job | 선행 조건 |
|-----------|-----|----------|
| 04:00 | 만료 `expireDailyJob` | — |
| 05:00 | 정산 `settleDailyJob` | 전일 만료 확정 후 |
| 06:00 | 대사 `reconcileDailyJob` | 정산까지 완료 후 |

### 스케줄을 놓친 날짜의 소급 실행

어드민 [배치] 탭 또는 API:

```bash
POST /admin/batch/expire/run    {"expireDate": "2026-08-13"}
POST /admin/batch/settle/run    {"settleDate": "2026-08-13"}
POST /admin/batch/reconcile/run {"reconcileDate": "2026-08-13", "externalFile": "/path/orders.csv"}  # 파일은 선택
```

- 같은 날짜 재실행은 안전하다: 만료는 데이터 레벨 멱등, 정산은 DRAFT만 재계산(확정분 동결), 대사는 미해결 이슈 중복 적재 없음.
- 이미 그 날짜가 완료된 만료 Job은 "이미 완료" 응답이 온다 — 정상이다 (JobInstance 멱등성).

### 배치 실패 시

```text
1. [배치] 탭 실행 이력에서 FAILED 확인 (종료 코드·파라미터)
2. 원인 제거 (DB 연결, 디스크 등)
3. 같은 날짜로 수동 재실행 — Spring Batch가 완료 청크를 스킵하고 실패 지점부터 재개
4. 재실행 후 대사 결과 확인 — 부분 실행이 남긴 불일치가 있으면 이슈로 드러난다
```

## 3. 장애 유형별 대응

| 장애 | 증상 | 대응 |
|------|------|------|
| 배치 도중 프로세스 사망 | 실행 이력 FAILED/UNKNOWN | 위 "배치 실패 시" — 재시작 멱등성이 이중 처리를 막는다 |
| 배치 이중 기동 (서버 2대) | — | 조치 불요. ShedLock이 한쪽만 실행, 뚫려도 UNIQUE 제약이 2차 방어 |
| DB 페일오버 순간 쓰기 실패 | 호출자에 5xx | 조치 불요. 호출자는 **같은 멱등성 키로 재시도** — 이중 기장 없이 안전. 커넥션은 HikariCP가 재수립 |
| 호출자 재시도 폭주 | 같은 키 409 다발 | `Retry-After: 1` 준수 여부 확인, API 키별 rate limit 검토 |
| 대사 불일치 발견 | 이슈 적재·대시보드 경고 | §1 절차 |

## 4. 접근·키 관리

| 항목 | 절차 |
|------|------|
| 운영자 계정 | 시드 계정 `admin@pointledger.io`, 비밀번호는 `PL_ADMIN_PASSWORD` 환경변수 |
| API 키 발급 | `POST /admin/api-keys` (ADMIN) — 원문은 발급 응답에서 단 한 번 노출, DB에는 SHA-256만 |
| 키 유출 시 | 해당 키 비활성화 후 재발급 — 원문 미저장이므로 유출 범위는 클라이언트 측에 한정 |
| 원장 보호 | 앱 DB 계정에 `ledger_entries` UPDATE/DELETE 권한을 부여하지 않는다 (append-only 트리거와 이중 방어) |

## 5. 모니터링 체크리스트 (일일)

```text
□ 대시보드 미해결 이슈 0건인가 — 아니면 §1
□ 배치 3종 실행 이력 COMPLETED인가 — 아니면 §2
□ 어제 정산서가 가맹점 수만큼 생성·확정됐는가
□ actuator/health UP (DB 연결 포함)
```
