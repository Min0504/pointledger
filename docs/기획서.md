# PointLedger — 포인트 월렛·정산 시스템

> **포트폴리오 포지션: 2순위 (SeatLock의 Spring 포팅 완료 후 시작).**
> 처음부터 끝까지 **순수 Java/Spring**으로 만드는 두 번째 프로젝트 — "포팅해 본 사람"에서 "Spring으로 설계하는 사람"으로 넘어가는 단계.
> 돈을 다루는 도메인이라 대기업·금융권 IT 면접 서사와 정확히 겹친다.
>
> 기존 자산과의 차별화: 오름장(학습 카드)은 에스크로 "거래 상태 전이"가 주제였다. PointLedger는 상태가 아니라 **원장(ledger) 정합성 — 이중 지급 방지, 격리수준, 대량 배치, 대사** — 가 주제다. SeatLock의 동시성이 "한 자원을 두 명이 잡는 문제"라면, 여기는 "한 잔액을 두 요청이 깎는 문제 + 기록의 감사 가능성"이다.

## 1. 프로젝트 기본 정보

| 항목 | 내용 |
|------|------|
| 프로젝트명 | PointLedger (포인트레저) |
| 한 줄 설명 | 적립·사용·만료·정산까지, 돈처럼 다뤄야 하는 포인트를 **append-only 원장**으로 관리하는 백오피스 시스템 |
| 목적 | 트랜잭션 격리수준·멱등성·배치 처리·대사(reconciliation)를 실제로 구현하고 "잔액이 절대 틀리지 않는 시스템"의 설계 원칙 증명 |
| 예상 사용자 | 가상의 이커머스 내부 시스템(주문 서버가 API 호출) + 운영자(백오피스) — B2B 내부 서비스 가정 |
| 핵심 문제 | 동시 사용 시 음수 잔액, 재시도로 인한 이중 적립/차감, 대량 만료 처리, 원장과 스냅샷 잔액의 불일치 |
| 해결 방법 | 원장 append-only + 잔액은 파생값, 멱등성 키, 격리수준·락 실험, Spring Batch 청크 처리, 일일 대사 배치 |
| 예상 개발 기간 | 6~8주 (주 15시간, Spring 학습 완료 상태 기준) |
| 난이도 | 중상 — 기능 수는 적지만 정합성 요구가 높다 (기능이 아니라 **불변식**을 구현하는 프로젝트) |
| 핵심 역량 | **트랜잭션·격리수준, 멱등성, 관계형 모델링(원장), Spring Batch, 테스트 설계, 감사(audit) 관점** |
| 클라이언트 | **웹 어드민(백오피스)** — 운영자 화면. `frontend/` 폴더 분리, 판단 근거는 §3 |

### 언어 선택 근거

- **Java 17 + Spring Boot 3 단독.** SeatLock 포팅으로 Spring 문법을 익힌 상태에서, 이번엔 백지에서 Spring으로 설계한다 — 이력서의 Java 줄에 "포팅 1 + 자체 설계 1"이 쌓여야 신입 Java 역량으로 인정받는다.
- 금융·대기업 SI가 요구하는 정확히 그 기술(JPA 심화, 트랜잭션 관리, 배치)을 정면으로 다룬다. 국내 기업 풀 70~80을 커버하는 메인 스택의 깊이 증명.

## 2. 핵심 기능 (기능마다 백엔드 문제 명시)

| 기능 | 내용 | 여기서 발생하는 백엔드 문제 |
|------|------|------------------------------|
| 지갑 생성/조회 | 사용자당 1지갑, 잔액·만료예정 조회 | 잔액 = 스냅샷인가 SUM(원장)인가 — 성능 vs 단순성 |
| **적립 (earn)** | 주문 적립, 프로모션 지급. 적립분마다 만료일 존재 | 재시도로 인한 **이중 적립** → 멱등성 키 |
| **사용 (redeem)** | 주문 결제 시 포인트 차감 | 동시 사용 → **음수 잔액**, 어느 적립분부터 쓸 것인가(FIFO) |
| 사용 취소 (cancel) | 주문 취소 시 차감 복원 | 이미 만료된 적립분으로의 복원은? 부분 취소는? — 도메인 규칙 설계 |
| **만료 (expire)** | 적립 후 365일 지나면 소멸, 매일 새벽 배치 | 수십만 행 일괄 처리, 배치 중단 후 재시작, 사용자 요청과의 경합 |
| 만료 예정 알림 데이터 | 30일 내 만료 예정 조회 API | 집계 쿼리 인덱스 설계 |
| 운영자 수동 지급/회수 | CS 보상 지급 등, 사유 필수 | **감사 로그** — 누가 언제 왜, 절대 수정·삭제 불가 |
| **정산 (settlement)** | 가맹점별 포인트 사용액 일일 집계 → 지급액 산출 | 집계 시점 경계(자정 걸친 트랜잭션), 재실행 멱등성 |
| **대사 (reconciliation)** | 원장 SUM vs 지갑 스냅샷, 내부 원장 vs 외부(주문 서버 mock) 기록 대조 | 불일치 탐지 시 처리 절차 — "틀렸을 때"의 운영 설계 |
| 원장 조회 | 사용자별 거래 이력 (커서 페이지네이션) | 대량 이력 조회 성능 |

의도적으로 뺀 것: 실 결제(PG)·상품·주문 도메인 전체 — 주문 서버는 mock으로 두고 **포인트 도메인의 깊이에 집중**한다. 숫자보다 퀄리티.

## 3. 기술 스택

| 구분 | 선택 | 이유 |
|------|------|------|
| 언어/프레임워크 | Java 17, Spring Boot 3.x | 메인 스택 심화. record·switch 패턴매칭 등 모던 Java 사용 |
| ORM | Spring Data JPA + QueryDSL | 원장 집계·동적 조회에서 QueryDSL 필요성이 자연 발생 |
| 배치 | **Spring Batch 5** | 만료·정산·대사가 전부 배치 도메인. chunk·restart·skip 정책이 곧 학습 내용 |
| DB | PostgreSQL 16 | CHECK 제약, 부분 인덱스, REPEATABLE READ 실험 |
| 분산 락 | ShedLock (JDBC 기반) | 다중 인스턴스에서 배치 중복 실행 방지 — Redis 없이 DB로 해결(인프라 최소화 판단) |
| 문서화 | SpringDoc(Swagger) + REST Docs 맛보기 | 테스트에서 문서를 생성하는 REST Docs는 대기업 실무 관행 |
| 인프라 | Docker Compose, GitHub Actions, EC2+RDS | SeatLock과 동일 패턴 재사용 — 인프라보다 도메인에 시간 배분 |
| 테스트 | JUnit5, Testcontainers, ArchUnit(선택) | 격리수준 실험은 실제 PostgreSQL이 필수라 Testcontainers 중심 |

Redis를 뺀 이유: 잔액은 캐시하면 안 되는 데이터(낡은 잔액 = 사고)고, 락은 DB 행 락과 ShedLock으로 충분하다. "Redis를 안 쓴 이유"를 말할 수 있는 것도 설계 능력이다.

### 클라이언트 결정 — 웹 vs 앱

| 후보 | 판단 |
|------|------|
| 모바일 앱 | 탈락 — 사용자가 "운영자(데스크 업무)"인 내부 시스템이라 모바일 시나리오 자체가 없음. 감사 관점에서도 관리 작업은 데스크 환경이 표준 |
| **웹 어드민 (채택)** | B2B 백오피스의 실무 표준. **원장 타임라인과 대사 이슈 처리 화면이 "감사·운영 절차" 서사를 눈으로 보여주는 최고의 데모** — 스크린샷·GIF로 GitHub 소개가 쉬워짐 |

- 스택: Vite + React + TypeScript(strict), 테이블 중심 UI. 화면 5개 — 대시보드(오늘 적립/사용/만료 집계) · 지갑 검색 → **원장 타임라인(엔트리별 잔액 변화 추적)** · 수동 지급/회수(사유 필수 폼 + 확인 모달) · 대사 이슈 목록/해결 처리 · 배치 실행 이력
- 서버 간 API(적립/사용)는 화면 없이 Swagger로 데모 — 어드민 화면과 역할이 다름
- 원칙: 프론트는 유리창 — AI 도구로 빠르게 생성, 전체 시간의 15% 상한

### Git·주석 전략 (커밋·푸시·PR·코드 주석) — 백엔드와 프론트를 다르게

> 원칙: **백엔드는 공부의 기록, 프론트는 결과물만.** 이 프로젝트의 커밋 이력은 "정합성 문제를 재현하고 해결한 순서" 그 자체여야 한다.

| 구분 | 백엔드 (학습의 본체) | 프론트엔드 (거들 뿐) |
|------|---------------------|---------------------|
| 커밋 | **재현 커밋 → 해결 커밋 쌍** — `test(redeem): READ COMMITTED lost update 재현(실패하는 테스트)` → `feat(redeem): 지갑 행 비관적 락으로 직렬화`. 실패하는 테스트를 지우지 않는다 | 화면 단위 뭉텅이 허용 — `fe: 원장 타임라인 화면` (AI 생성 코드 그대로 OK) |
| 브랜치 | GitHub Flow. 핵심 문제(§7) 1개 = 브랜치 1개 — `feat/idempotency-key`, `feat/expire-batch`, `feat/reconcile-job` | `fe/admin` 브랜치 하나로 진행 |
| PR | **혼자여도 PR을 연다** — 본문에 불변식·격리수준 실험 결과 기록, CI(불변식 프로퍼티 테스트 포함) 초록 없이 머지 금지 | 생략 가능(main 직행) 또는 1개 — 어드민 스크린샷이면 충분, squash 머지 |
| PR 단위 | 핵심 문제 1개 = PR 1개, 배치 Job은 Job당 1개 | 프로젝트 전체에서 PR 1개 |
| 푸시 | 매일 푸시, main force push 금지 | 동일 |
| 이력 관리 | 낙관적 락 비교 브랜치(`experiment/optimistic-retry`)는 머지하지 않고 보존 → README 링크 | 이력 가치 없음 |

**주석 규칙 — 코드가 곧 교재가 되도록:**

- **백엔드: 핵심 로직마다 설명 주석 필수.** "무엇을 하는지"가 아니라 **왜 이 방식인지**(문제 상황 → 대안 → 선택 이유)를 적는다. 예 — `SELECT ... FOR UPDATE` 위에: `// READ COMMITTED에서는 두 커넥션이 같은 잔액을 읽고 각자 차감해 lost update 발생(재현: RedeemConcurrencyTest) → 지갑 행 비관적 락으로 직렬화. 낙관적 락 재시도 방식과의 비교는 experiment/optimistic-retry 브랜치`. 트랜잭션 경계·격리수준 선택마다 이유를 남긴다.
- **프론트: 주석 최소.** AI가 생성한 어드민 코드 그대로 두고, 백엔드 계약과 닿는 지점(멱등키 헤더 전송, 잔액 불일치 표시)에만 한 줄 남긴다.

## 4. 아키텍처

```
[주문 서버 (mock)]        [웹 어드민 (frontend/) — 운영자]
        │  REST (서버 간: API Key, 운영자: JWT+RBAC)
        ▼
[PointLedger API — Spring Boot]
        │   ├─ WalletService      (잔액 조회·검증)
        │   ├─ LedgerService      (적립/사용/취소 — 모든 변경은 원장 경유)
        │   ├─ IdempotencyFilter  (멱등성 키 선점)
        │   └─ AdminService       (수동 지급/회수 + 감사 로그)
        ▼
[PostgreSQL 16 (RDS)]  ←— 유일한 상태 저장소. 원장이 진실, 잔액은 파생
        ▲
[Spring Batch (같은 코드베이스, 별도 프로세스로 기동)]
        ├─ ExpireJob   (매일 04:00 — 만료 처리)
        ├─ SettleJob   (매일 05:00 — 가맹점 정산)
        └─ ReconcileJob(매일 06:00 — 원장 vs 스냅샷 vs 외부 기록 대조)
             └─ 불일치 발견 시: reconcile_issues 기록 + 운영자 조회 API
[ShedLock 테이블] — 배치 인스턴스 간 상호 배제
```

핵심 구조 원칙: **모든 포인트 변화는 반드시 ledger_entries INSERT를 동반한다.** 지갑 잔액을 직접 UPDATE하는 코드 경로는 존재하지 않는다(잔액 갱신은 원장 기록과 같은 트랜잭션에서만). 이 규칙을 ArchUnit 테스트로 강제하는 것까지가 설계다.

## 5. 데이터베이스 설계

### wallets — 지갑 (잔액 스냅샷)
| 컬럼 | 타입 | 제약 |
|------|------|------|
| id | BIGSERIAL PK | |
| user_id | BIGINT | UNIQUE, NOT NULL (사용자당 1지갑) |
| balance | BIGINT | NOT NULL, **CHECK (balance >= 0)** — 최후 방어선 |
| version | INT | 낙관적 락 실험용 (@Version) |
| updated_at | TIMESTAMPTZ | |

> balance는 **파생값(원장의 SUM과 항상 일치해야 함)**. 조회 성능 때문에 두지만, 진실은 원장이다. 이 불일치 가능성을 대사 배치가 매일 검증한다 — "비정규화를 했으면 검증 장치가 따라와야 한다"는 원칙의 실물.

### ledger_entries — 원장 ★ append-only, 이 프로젝트의 심장
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | |
| wallet_id | BIGINT FK→wallets | 인덱스 `(wallet_id, id DESC)` — 이력 조회 |
| type | VARCHAR(20) | 'EARN' / 'REDEEM' / 'CANCEL' / 'EXPIRE' / 'ADMIN_GRANT' / 'ADMIN_REVOKE' |
| amount | BIGINT | **양수 고정.** 방향은 type이 결정 (부호 실수 원천 차단) |
| balance_after | BIGINT | 기록 시점 잔액 — 감사·디버깅용 스냅샷 |
| ref_type / ref_id | VARCHAR / VARCHAR | 출처 (ORDER/PROMO/CS 등 + 외부 ID). 인덱스 |
| idempotency_key | VARCHAR(64) | **UNIQUE (부분 인덱스: WHERE idempotency_key IS NOT NULL)** |
| reason | VARCHAR(200) | ADMIN 계열은 NOT NULL (운영 규칙을 스키마로 강제) |
| created_by | VARCHAR | 시스템/운영자 식별 — 감사 |
| created_at | TIMESTAMPTZ | |

> **UPDATE/DELETE 금지 테이블.** 정정은 반대 방향 엔트리 추가로만(회계의 붉은 줄 원리). DB 권한에서 앱 계정에 UPDATE 권한 자체를 주지 않는 것까지 실험한다.

### point_lots — 적립 단위(로트), FIFO 만료의 기반
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | |
| wallet_id | BIGINT FK | |
| earn_entry_id | BIGINT FK→ledger_entries | 이 로트를 만든 적립 기록 |
| initial_amount | BIGINT | 적립액 |
| remaining | BIGINT | **CHECK (remaining >= 0 AND remaining <= initial_amount)** |
| expires_at | TIMESTAMPTZ | 인덱스 `(expires_at) WHERE remaining > 0` — 만료 배치 스캔용 부분 인덱스 |
| status | VARCHAR | 'ACTIVE' / 'EXHAUSTED' / 'EXPIRED' |

### lot_consumptions — 사용이 어느 로트에서 나갔는지 (사용↔로트 N:M 해소)
- id PK, redeem_entry_id FK, lot_id FK, amount
- **왜 필요한가:** "3,000P 사용"이 로트 A(2,000)와 B(1,000)에서 나갔다는 사실을 기록해야 ① 사용 취소 시 원래 로트로 복원 가능 ② 만료 계산이 정확해진다. 이 테이블이 없으면 취소·만료가 뒤엉킨다 — 모델링 면접 단골 소재.

### merchants / settlements / settlement_lines — 정산
- merchants: id PK, name, status
- settlements: id PK, merchant_id FK, settle_date DATE, total_amount, status('DRAFT'/'CONFIRMED'), **UNIQUE(merchant_id, settle_date)** — 재실행해도 중복 정산서가 안 생기는 멱등성의 근거
- settlement_lines: settlement_id FK, ledger_entry_id FK **UNIQUE** — 한 거래가 두 정산서에 들어가는 사고 차단

### reconcile_issues — 대사 불일치 기록
- id PK, job_run_id, issue_type('SNAPSHOT_MISMATCH'/'EXTERNAL_MISSING'/'INTERNAL_MISSING'), wallet_id, expected/actual, resolved(BOOLEAN), memo

### idempotency_requests — 멱등 요청 상태 (처리중/완료 응답 보관)
- key VARCHAR PK, request_hash, status('IN_PROGRESS'/'DONE'), response_body JSONB, expires_at(7일 후 정리 배치)

## 7. 핵심 백엔드 문제 (문제→원인→해결→선택 이유→비교→트레이드오프)

### 문제 1. 동시 사용으로 인한 음수 잔액 (lost update)

- **문제:** 잔액 5,000P에서 3,000P 사용 요청 2개가 동시 진입 → 둘 다 "잔액 충분" 판정 → 잔액 -1,000P.
- **원인:** READ COMMITTED에서 두 트랜잭션이 같은 스냅샷(5,000)을 읽고 각자 갱신 — 전형적 lost update. **먼저 테스트로 재현해 커밋에 남긴다.**
- **해결(채택): 지갑 행 비관적 락 직렬화**
  ```java
  @Lock(LockModeType.PESSIMISTIC_WRITE)   // SELECT ... FOR UPDATE
  Optional<Wallet> findByUserIdForUpdate(Long userId);
  ```
  트랜잭션: 락 획득 → 잔액 검증 → 로트 FIFO 차감 → 원장 INSERT → 잔액 UPDATE → 커밋.
- **왜:** 포인트 사용은 로트 차감·원장 기록까지 **다단계 로직**이라 SeatLock의 한 줄 조건부 UPDATE로 못 푼다. 지갑 단위 직렬화가 정확성 대비 가장 단순하다. 같은 사용자의 동시 결제는 드물어 락 경합 비용도 낮다(핫스팟이 자원(좌석)이 아니라 사용자라는 도메인 차이 — SeatLock과의 대비가 곧 면접 답변).
- **비교:** ① 낙관적 락(@Version+재시도): 구현해서 브랜치로 남기되, 다단계 쓰기의 재시도 복잡도가 높음을 기록 ② `UPDATE wallets SET balance = balance - :amt WHERE balance >= :amt`: 잔액만이면 충분하지만 로트 차감을 못 담음 ③ SERIALIZABLE 격리: 가장 선언적이나 재시도 처리 필수 + PostgreSQL SSI 학습 겸 실험만.
- **트레이드오프:** 비관적 락은 커넥션 점유 시간을 늘린다 → 트랜잭션 안에서 외부 호출 금지 원칙과 함께 설계. CHECK(balance>=0)는 버그가 뚫려도 DB가 막는 최후 방어선으로 이중화.

### 문제 2. 재시도로 인한 이중 적립/이중 차감

- **문제:** 주문 서버가 타임아웃 후 재시도 → 같은 주문으로 적립이 2번 발생.
- **원인:** 네트워크는 "요청이 처리됐는지"를 알려주지 않는다. at-least-once 재시도는 호출자의 합리적 행동이고, 중복 제거는 수신자(우리)의 책임.
- **해결(채택):** `Idempotency-Key`(주문번호 기반) → idempotency_requests에 INSERT로 선점(PK 충돌 = 중복) → IN_PROGRESS면 409, DONE이면 **저장된 응답 그대로 반환**. ledger_entries.idempotency_key UNIQUE가 2차 방어.
- **왜:** 상태(IN_PROGRESS/DONE)와 응답 보관까지 있어야 "처리 중 재시도"와 "완료 후 재시도"를 다르게 답할 수 있다 — 키 유무만 보는 단순 구현과의 차이.
- **비교:** DB 유니크 제약만(응답 재현 불가, 처리중 구분 불가) / Redis SETNX(만료로 증발하면 이중 지급 — 돈 관련 기록은 영속 필요). Stripe·Toss Payments의 공개 API 설계가 이 패턴의 실제 사례 — 문서에 레퍼런스로 남긴다.
- **트레이드오프:** 응답 보관 테이블이 자라므로 7일 후 정리 배치 필요. request_hash 비교로 같은 키에 다른 바디가 오면 422 — 키 재사용 실수를 조기에 드러낸다.

### 문제 3. 잔액 스냅샷과 원장의 정합성 — 왜 둘 다 갖는가

- **문제:** 잔액을 원장 SUM으로 계산하면 항상 정확하지만 이력이 수만 건이면 조회마다 집계 비용 발생. 스냅샷을 두면 빠르지만 어긋날 수 있다.
- **원인:** 성능을 위한 비정규화는 정합성 검증 의무를 낳는다.
- **해결(채택):** 스냅샷 + **같은 트랜잭션에서 원장과 잔액을 함께 갱신** + balance_after 기록 + **매일 대사 배치가 wallet.balance == SUM(ledger) 전수 검증**, 불일치는 reconcile_issues로.
- **왜:** "빠른 조회"와 "검증 가능한 진실"을 둘 다 가진다. balance_after 덕에 불일치 발생 지점을 이력에서 이분탐색으로 찾을 수 있다.
- **비교:** 이벤트 소싱 풀 구현(스냅샷+리플레이)은 이 규모에 과함 — 다만 원장=이벤트, 잔액=프로젝션이라는 관점의 축소판임을 설명할 수 있게 정리. 잔액 테이블 없이 SUM만 쓰는 안은 이력 1만 건+p95 요구가 생기는 순간 무너짐을 벤치마크로 보인다.
- **트레이드오프:** 쓰기마다 지갑 행 갱신이 동반돼 쓰기 경로가 무거워진다 — 문제 1의 락과 결합해 "지갑 단위 직렬화"로 일관.

### 문제 4. FIFO 만료 배치 — 수십만 로트를 안전하게

- **문제:** 매일 새벽, 만료일이 지난 로트의 remaining을 EXPIRE 원장으로 소멸시켜야 한다. 대상이 수십만 건이고, 도중에 죽을 수 있고, 그 시각에도 사용자는 포인트를 쓴다.
- **원인:** 대량 + 부분 실패 + 온라인 경합이 겹치는 전형적 배치 문제.
- **해결(채택): Spring Batch chunk 방식**
  - Reader: `expires_at < today AND remaining > 0` 로트를 id 순 페이징 조회 (부분 인덱스 활용)
  - Processor→Writer: 청크(500건) 단위 트랜잭션 — 로트 EXPIRED 처리 + EXPIRE 원장 INSERT + 지갑 잔액 차감(지갑 행 락 — 온라인 요청과 동일한 락 규약이라 경합해도 정합성 유지)
  - 실패 시 해당 청크만 롤백, JobRepository 메타데이터로 **이어서 재시작**
  - ShedLock으로 다중 인스턴스 중복 기동 차단
- **왜:** 단일 거대 트랜잭션(수십만 행)은 롤백 비용·락 범위·undo 부담이 재앙이다. 청크는 실패 반경을 500건으로 제한한다.
- **비교:** @Scheduled+수동 페이징 루프로도 가능하나 재시작 지점 관리·skip 정책·실행 이력을 전부 손으로 짜게 된다 — Spring Batch가 표준인 이유를 몸으로 이해하는 게 학습 목표. Kafka 등 스트림 처리는 "매일 새벽 일괄"이라는 요구에 부적합.
- **트레이드오프:** Spring Batch의 러닝커브(JobRepository 스키마, Step 구성)가 있다 — 그 자체가 대기업 실무 기술이라 투자 가치 있음. 청크 사이즈는 500/1000/5000 벤치마크로 근거를 만든다.

### 문제 5. 정산·대사 — "틀렸을 때"를 설계하기

- **문제:** 가맹점 정산액이 내부 원장과 외부(주문 서버) 기록과 다르면? 배치를 두 번 돌리면 정산이 중복되나?
- **원인:** 분산된 두 시스템의 기록은 반드시 어긋날 수 있다(전송 유실, 시각 경계, 버그). "안 틀리게"만이 아니라 "틀림을 발견하고 수습하는" 절차가 시스템의 일부여야 한다.
- **해결(채택):** ① 정산 멱등성 — UNIQUE(merchant_id, settle_date) + settlement_lines의 entry UNIQUE로 재실행 안전 ② 대사 3단 — 스냅샷 vs 원장 SUM / 내부 원장 vs 외부 mock CSV(양방향 누락 검출) / 정산서 vs 원장 합계 ③ 불일치는 자동 수정하지 않고 reconcile_issues에 적재 → 운영자 확인 후 정정 엔트리(ADMIN_GRANT/REVOKE + reason)로만 수습.
- **왜:** 돈 관련 자동 보정은 버그가 버그를 덮는 경로다. "탐지는 자동, 수정은 사람"이 실무 원칙.
- **비교:** 불일치 즉시 예외/중단(운영 불가), 로그만 남김(발견 안 됨) 대비, 이슈 테이블+운영 API가 균형점.
- **트레이드오프:** 운영자 손이 가는 설계 — 신입 포트폴리오에서 "운영 절차까지 설계했다"는 희소 시그널이 된다.

## 10. 장애 대응

| # | 장애 | 대응 설계 |
|---|------|-----------|
| 1 | **배치 도중 프로세스 사망** | Spring Batch 재시작 — 완료 청크는 건너뛰고 실패 지점부터. "재실행해도 이중 만료 없음"을 테스트로 증명 (로트 status 조건이 멱등성 보장) |

| 3 | **DB 페일오버 순간 쓰기 실패** | 호출자에게 5xx + 재시도 안내 → 멱등성 키 덕분에 재시도가 안전하다는 것이 곧 장애 대응력. 커넥션 재수립은 HikariCP 검증 쿼리로 |
| 4 | **대사 불일치 발견** | 자동 수정 금지 → issue 적재 → 운영자 정정 절차(문서화된 runbook). 모의 시나리오: 원장 한 건을 수동 조작 후 대사가 잡아내는 데모 |
| 5 | 호출자(주문 서버)의 무한 재시도 폭주 | 409 IN_PROGRESS 응답 + Retry-After 헤더, 키별 rate limit |

각 시나리오는 재현 방법과 함께 `docs/incident/`에 리포트로 남긴다.

## 11. 테스트 전략

| 레벨 | 도구 | 반드시 검증할 것 |

GitHub Actions (test → build → GHCR) → EC2 docker compose

## 13. 개발 단계

| Phase | 내용 | 완료 기준 |
|-------|------|-----------|
| 1 | 지갑·원장·적립/사용 (동시성 무시, happy path) | 원장 경유 규칙 성립, 잔액 조회 동작 |
| 2 | **lost update 재현 → 비관적 락 적용** | 재현 테스트(락 없음, 실패)와 해결 테스트(락, 통과)가 커밋 이력으로 공존 |
| 3 | 멱등성 키 (요청 상태 테이블 + 응답 재현) | 동시 중복·완료 후 재시도 테스트 통과 |
| 4 | 로트 FIFO·사용 취소·수동 지급(감사) | 불변식 프로퍼티 테스트 통과 |
| 5 | **Spring Batch 만료 Job** (+ ShedLock) | 중단 후 재시작 테스트 통과 |
| 6 | 정산 Job + 대사 Job + 이슈 운영 API | 불일치 모의 시나리오 데모 |

## 14. 학습 가이드 — 코드를 하나씩 보며 공부하는 법

**규칙: 재현 커밋 → 해결 커밋을 쌍으로.** "버그가 있는 코드"를 지우지 말고 이력으로 남긴다 — 이것이 남들과 다른 학습형 저장소를 만든다.

| Phase | 여기서 공부하는 개념 | 끝나고 스스로 답할 질문 |
|-------|---------------------|------------------------|
| 1 | JPA 엔티티 설계, 연관관계 방향, append-only 모델링 | "잔액을 UPDATE하는 코드가 왜 LedgerService 한 곳에만 있는가?" |
| 2 | 격리수준 4단계, lost update, FOR UPDATE, 데드락 | "READ COMMITTED가 이 버그를 못 막는 이유를 스냅샷 관점으로 설명할 수 있는가?" |
| 3 | 멱등성, at-least-once, HTTP 재시도 의미론 | "타임아웃은 실패인가? 모른다는 상태를 어떻게 다루는가?" |
| 4 | 도메인 불변식, CHECK 제약, 프로퍼티 기반 테스트 | "이 시스템에서 절대 깨지면 안 되는 문장 3개를 말할 수 있는가?" |
| 5 | Spring Batch 구조(Job/Step/Chunk), 재시작성, ShedLock | "청크 500의 트랜잭션 경계는 정확히 어디부터 어디까지인가?" |
| 6 | 대사, 비정규화의 검증 의무, 운영 절차 설계 | "불일치를 자동 수정하면 안 되는 이유는?" |

**코드 읽기 순서:** ① 엔티티(ledger/lot) ② LedgerService.redeem(락→검증→차감→기록) ③ 격리수준 재현 테스트 ④ IdempotencyFilter ⑤ ExpireJob Step 구성 ⑥ ReconcileJob.
**블로그 소재:** lost update를 테스트로 재현하기 / 멱등성 키 설계(Stripe 패턴) / Spring Batch 재시작 실험 / 원장 SUM vs 스냅샷 벤치마크.

## 15. 이 프로젝트로 증명할 수 있는 역량

- 트랜잭션 격리수준을 **암기가 아니라 재현 실험**으로 이해
- 멱등성·감사 가능성 등 **돈을 다루는 시스템의 설계 원칙** (금융·대기업 서사 직결)
- 관계형 모델링 깊이 (원장/로트/소비 — "왜 이 테이블이 필요한가"를 전부 답할 수 있는 스키마)
- Spring Batch 실전 (chunk·재시작·분산 락) — 신입 중 보유자가 드문 기술
- 불변식 중심 테스트 설계

## 16. 면접 예상 질문 (12)

1. lost update가 발생하는 격리수준과 그 이유는? REPEATABLE READ면 해결되나? (PostgreSQL의 스냅샷 격리 특성 포함)
2. 왜 SeatLock에서는 조건부 UPDATE로 충분했는데 여기서는 비관적 락을 썼나?
3. 트랜잭션 안에서 외부 API를 호출하면 안 되는 이유는? 지금 코드의 트랜잭션 범위는 정확히 어디까지인가?
4. 멱등성 키를 DB에 저장할 때 "처리 중" 상태가 왜 필요한가? 없으면 어떤 시나리오가 뚫리나?
5. 잔액을 원장 SUM으로만 계산하지 않고 스냅샷을 둔 이유와, 그로 인해 생긴 의무는?
6. amount를 항상 양수로 두고 type으로 방향을 정한 이유는?
7. 원장 테이블에 UPDATE 권한을 아예 주지 않았다 — 정정이 필요하면 어떻게 하나?
8. 만료 배치가 도는 동안 사용자가 그 로트로 결제하면 어떻게 되나? (락 규약 일관성)
9. 청크 크기를 어떻게 정했나? 크면/작으면 각각 무엇이 나빠지나?
10. 배치가 두 서버에서 동시에 뜨면? ShedLock이 실패하면? (계층 방어)
11. 대사에서 불일치가 나왔을 때의 처리 절차는? 왜 자동 보정하지 않나?
12. 이 시스템이 절대 위반하면 안 되는 불변식들을 말하고, 각각 어느 계층(코드/제약/배치)이 지키는지 설명하라.
